# Codex 原生宿主执行桥接计划

- 状态：已完成（策略由后续计划取代，真实宿主闭环已在后续验收中打通）
- 创建日期：2026-10-03
- 最后更新：2026-10-03
- 负责人：ZCode 整合；核心存储、MCP 验证、UI 分文件负责（见本次实施记录）
- 关联历史记录：[本次实现](../../histories/2026-10/20261003-2120-codex-native-execution-bridge.md)

## 目标

让 TaskLane 卡片绑定真实 Codex Desktop 聊天：用户从看板发起执行请求，
由 Codex 宿主创建或续接聊天，在正确工作区执行，再通过 TaskLane MCP
回写真实聊天标识与执行回执。用户能够从卡片打开关联聊天。

**不在 Codex 宿主中运行时，默认不执行。** 不通过 CLI、App Server、
后台进程或其他 Agent 兜底；不能以看板状态变更冒充真实执行。

## 范围

- 第一阶段：宿主能力探测、用户请求传递、创建真实聊天、绑定、打开、
  最小执行回执闭环、宿主文案适配，以及非 Codex 环境的默认不执行行为。
- 后续阶段：绑定聊天的回复、继续执行、重试、结果与错误反馈。
- 停止操作：仅在验证宿主具备真实停止能力后实现；此前禁用并说明原因。
- 不包含：自建 Codex App Server、CLI 执行器、桌面私有接口注入、
  自动提交/合并、删除聊天或工作区、完整日志流和定时后台执行。
- 本次已实现本地协议、存储、UI 与技能；不创建真实聊天或启动 Agent。真实宿主验证尚未解除前置门槛。

- `ui/src/host.ts` 的 `window.tasklaneHost` 是项目自定义约定，只有声明和

## 已选架构

```text
TaskLane UI：用户明确点击执行、继续或打开聊天
  → MCP Apps：向关联宿主聊天发送用户请求
  → Codex Agent：读取任务，调用原生聊天/工作区工具
  → TaskLane MCP：绑定真实 threadId，回写执行回执
  → TaskLane UI：刷新卡片、详情与打开聊天入口
```

- TaskLane 负责任务规则、请求记录与聊天绑定。
- Codex 宿主负责真实聊天、执行、审批及新工作区生命周期。
- UI 不能把宿主的聊天工具当作 TaskLane MCP 工具直接调用。
  `create_thread`、`send_message_to_thread`、`navigate_to_codex_page` 等
  由接收请求的 Agent 调用，并以届时实际工具可用性为准。
- 保留 MCP Apps 看板数据通道；将执行入口改为应用自身实现的异步宿主
  适配层，替代等待 `window.tasklaneHost` 注入的旧路径。

## 实现路径

### 阶段一：先验证宿主能力和消息路由

1. 核对安装版本的 MCP Apps SDK，封装 `sendMessage`、`openLink`、
   能力读取及错误响应。SDK 方法存在或 bundle 被注入不等于宿主支持。
2. 能力探测默认关闭执行。只有确认是 Codex 宿主、消息路由可用，并能由
   接收方调用所需原生工具后，才开放对应执行能力；未知环境默认不执行。
3. 分别验证项目聊天入口和全局侧边栏入口。项目模式保持 `lockedBoardId`；
   全局模式先选择目标看板，并确认用户请求送往哪个聊天。
4. 全局入口若没有接收聊天，展示限制；可提供由用户主动点击的项目聊天
   深链接。链接预填提示只代表准备输入，不能记作已执行。
5. 验证真实线程深链接 `codex://threads/<threadId>` 是否能从 widget 打开。
   若 `openLink` 拒绝该协议，可通过宿主 Agent 请求导航；无可用路径则
   提示能力不可用，不复制 `sess-*` 冒充可打开的真实聊天 ID。

本阶段为实施前置验证。官方协议和本地 SDK 的能力，不能直接写成当前
桌面宿主已经支持；需要记录实际版本、入口、请求结果和展示结果。

### 阶段二：建立请求与真实聊天绑定

1. 在核心模型中区分内部 `sessionId` 和真实聊天绑定。建议新增独立的
   `executionBinding`，记录 `provider: codex-desktop`、`threadId`、
   `hostId`、执行目录、工作区所有者及绑定时间；实际结构在实现前固定。
2. 新增受核心规则约束的执行请求记录，包含 `requestId`、任务/看板 ID、
   动作、请求状态和时间。新一轮执行使用独立 `runId`，区分重试及旧回执。
3. 增加请求、绑定和回执 MCP 契约。拟定入口为
   `task_execution_request`、`task_execution_bind`、`task_execution_report`；
   最终名称、参数、返回结构和错误码在本阶段固定并写契约测试。
4. 用户点击创建独立执行聊天后，先记录请求，再用 `sendMessage` 发送
   用户可读的明确指令，包含任务 ID、看板 ID、请求 ID 和目标仓库。
   任务描述由 Agent 通过 `task_get` 获取，作为任务内容，不作为宿主控制指令。
5. Agent 根据实际可用工具读取项目列表、选择匹配项目并创建聊天。
   `create_thread` 返回创建中标识时保持等待；只有真实 `threadId` 和
   `hostId` 就绪后才能绑定。创建成功不等于执行已开始。
6. 新增原生执行技能，指导接收请求的 Agent 完成创建、绑定、回执和错误
   处理。技能明确限定用户请求范围，不自动向无关聊天发送消息。
   技能名称由实现阶段确定，并按插件构建流程分发。
7. 双击及重复消息复用同一请求；同一任务不并发创建多个聊天。
   记录创建结果后再绑定，绑定失败允许恢复。超时显示“结果待确认”，
   不自动再创建一个聊天；先核对原请求是否已创建成功。

### 阶段三：固定工作区所有权

- 新增原生执行任务的工作区由 Codex 管理；TaskLane 保存宿主返回的目录、
  分支和绑定，不在指派时重复创建 worktree。
- 用户界面必须明确选择工作方式。创建独立 worktree 的请求需要写清
  “新建聊天并在独立 worktree 执行”，不能从普通指派操作隐式推导授权。
- 普通 `task_assign` 只改变负责人，不启动 Agent，也不作为执行请求。
  将现有分支/worktree 创建与指派解耦，检查所有 UI/MCP 调用方和测试。
- 旧任务已有 TaskLane worktree 时完整保留；先验证原生工具能否绑定或
  在该目录创建聊天。不可复用时显示限制，不能静默切回主仓库或另建目录。
- 非 Codex 环境指派、状态流转仍属普通看板操作，不调用任何执行器，
  不自动创建分支/worktree。用户已有 Git 绑定不因此被清空。
- 无提交仓库或基线不可用时，保留任务管理能力，按实际宿主能力提示；
  不为创建工作区自动生成首次提交。

### 阶段四：执行态改为回执驱动

1. `doing` 表示业务阶段，不自动把 `execution.state` 设为 `running`。
   执行请求等待时可用 `starting`；真实启动得到确认后才设置 `running`
   和 `startedAt`。消息投递成功、聊天创建成功均不能作为启动证据。
2. 原生执行技能要求目标聊天通过 MCP 报告实际开始、等待输入、失败和
   本轮完成。没有事件订阅时明确使用 Agent 回报机制，不宣称实时进程监控。
3. 回执必须匹配任务、看板、绑定聊天和当前 `runId`；锁内验证后只合并
   对应字段，保留并发编辑。旧回执不得覆盖新的执行，归档任务遵守归档守卫。
4. 回复和重试向已绑定聊天发送明确用户请求，保留完整回复文本，不以
   `activity` 摘要代替。请求被接收不代表恢复运行，执行态仍等待回执。
5. 停止能力独立探测；无专用宿主停止接口时禁用 Stop。向聊天发送
   “停止”文字不等于可靠中断，改派 human 不写入真实停止事件。
6. 断连、超时或未知结果显示待确认信息，不伪造成功、失败或已停止。
   UI 不支持执行时显示原因，不触发执行请求或写入运行态。

### 阶段五：整合界面与文档

- 卡片和详情展示“未绑定 / 请求中 / 已绑定 / 等待回执”等实际信息。
  「打开聊天」使用真实绑定；旧 `sess-*` 可以保留为内部标识，但不作为
  真实聊天链接，也不显示“已创建 Codex 会话”的成功提示。
- 窄栏、宽视图及全局看板复用同一执行操作层，捕获点击时的任务、看板和
  请求 ID；切换看板时废弃旧 UI 响应，服务端仍校验任务归属。
- 无宿主、其他 MCP Apps 宿主、能力缺失或未确认时，执行按钮禁用并说明
  具体原因，文案按下方规则适配。普通创建、编辑、归档和手动流转继续可用。
- 更新 README、WORKFLOW、extension 说明及插件技能，删除旧注入约定和
  “指派即创建真实会话”的错误描述，不保留无实际使用者的兼容执行分支。

### 宿主文案适配规则

**确认处于 Codex 宿主时使用 Codex 文案；其他环境和身份未知时使用 Agent
通用文案。** 文案选择与执行能力分开判断：识别到 Codex 不等于具备所有
执行能力，显示 Agent 也不意味着接入了其他执行器。

| 操作 | 已确认 Codex 宿主 | 其他环境或身份未知 |
| --- | --- | --- |
| 执行 | 在 Codex 中执行 | 在 Agent 中执行 |
| 继续 | 在 Codex 中继续执行 | 在 Agent 中继续执行 |
| 打开会话 | 打开 Codex 会话 | 打开 Agent 会话 |
| 回复 | 回复 Codex | 回复 Agent |
| 重试 | 在 Codex 中重试 | 在 Agent 中重试 |
| 停止 | 停止 Codex 执行 | 停止 Agent 执行 |

- 在宿主适配层分别提供宿主身份和操作能力；通过可信的宿主上下文确认
  身份，不根据 `sess-*`、真实绑定字段、SDK 注入或浏览器 URL 猜测。
- 卡片、详情、菜单、提示及无障碍名称使用同一份文案映射，避免同一环境
  混用 Codex 和 Agent。看板里的通用负责人类型 `agent` 不因文案变化改名。
- 已确认 Codex 但具体能力不可用时，保留 Codex 操作文案并禁用该入口，
  例如提示“当前 Codex 宿主未提供会话打开能力”。
- 非 Codex 或身份未知时，保留 Agent 通用文案，执行类入口禁用，提示
  “当前环境未接入 Agent 执行能力”；仍遵守默认不执行，不启用任何兜底执行器。
- 能力探测完成、重连或上下文变化后，统一刷新文案和可用状态；
  仅更新文案不能触发请求、创建聊天或修改执行态。

## 风险、兼容与回滚

- 宿主消息投递和工具调用不是同一个原子事务：使用持久化请求、幂等绑定、
  明确回执和恢复流程；请求 ID 只用于关联，不能宣称它提供身份认证。
- widget 自报字段和任务描述不可信。Agent 重新读取任务、验证项目和目录，
  不把任务文字解释为删除、提交或向其他聊天发消息的额外授权。
- `sessionId` 旧数据缺少真实绑定时按未绑定处理，不转换为 `threadId`。
  旧 running 也不证明真实进程存活，显示未核实且不得据此自动续接执行。
- 拟新增字段的版本和迁移必须基于执行时最新存储设计，协调归档 v3 改动。
  涉及版本升级时停用旧写进程、锁内检查版本、备份并原子落盘，验证旧数据
  的任务、时间线、ID 序列、归档字段及 Git 绑定均保留。
- 请求、绑定和时间线的持久化与并发策略由核心负责；不能只靠 UI 禁用按钮
  防重复，也不能用旧任务副本覆盖新的字段。
- 回滚前停止新的请求入口，保存当前数据和已创建聊天/工作区映射。
  已有新写入时禁止直接用旧备份覆盖；先确定无损回迁方式。
  回滚不删除真实聊天、分支或 worktree，不自动重启或停止真实 Agent。

## 验证方式与验收标准

- 核心/MCP：`pnpm build`、`pnpm test`、`pnpm smoke`。
- 存储并发：`pnpm verify:twoproc`；Git 创建逻辑调整后运行 `pnpm verify:git`。
- UI：`pnpm --filter @tasklane/ui typecheck`、`pnpm build:ui`。
- 插件：`pnpm build:plugin`、`pnpm verify:plugin`；构建产物按仓库规定处理。
- 后台自动化测试设置最长 60 秒硬超时，使用临时数据和临时 Git 仓库。
  真实宿主验收使用专门测试任务与明确授权的测试聊天，不操作已有真实任务。
- 内置 Chrome 验证独立模式、窄栏、宽视图、断连及错误态；Codex 原生宿主
  单独验收，浏览器模拟结果不能证明真实聊天创建与执行成功。
