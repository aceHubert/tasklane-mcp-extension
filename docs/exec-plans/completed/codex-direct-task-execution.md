# Codex 握手后直接提交任务

- 状态：已完成（协议由[分发任务 ID 计划](task-id-direct-execution.md)接续并完成原生验收）

- 最后更新：2026-10-04

- 关联历史记录：待整合验证后填写

## 目标

已连接且实时识别为 Codex 的面板直接提交用户选择的任务，不再创建独立验证聊天或
依赖过期声明。接收 Agent 在实际任务中核对原生工具和工作区，立即保存真实聊天标识，
created→bound 后才执行正文；成功投递不冒充真实执行，明确拒绝报错，未知结果可核对且不重复创建。

## 范围

- 包含：UI 入口和诊断、任务请求/认领身份、投递拒绝、提示词和执行技能、插件构建与说明。
- 不包含：CLI/App Server 兜底、Stop、任意旧工作区自动迁移、代码提交、自动启动用户的手动测试任务。

## 背景

- 前一方案把 nativeExecution 声明放进一次性 open_tasklane 结果；另一面板无法继承，
  短 TTL 和新测试聊天导致用户反复验证。用户明确选择改为实际任务内验证。
- 相关代码：`ui/src/host.ts`、`ui/src/mcp/appsClient.ts`、`packages/core/src/native-execution.ts`。
- [当前原生契约](../../native-execution-contract.md)、[先前原生计划](codex-native-execution-bridge.md)。

## 风险

- 面板在投递前不知道真实 receiver：初始路由可省略，实际认领必须核对成对的原生标识，
  存入 receiver；不伪造 sess-*，不把新任务目标聊天当作接收聊天。
- 未知创建结果重复：唯一 claim、同结果两阶段绑定、结果未知保留待确认，禁止重建。
- 拒绝与运行混淆：rejected 是投递/接收拒绝，不写 failed/running/startedAt；迟到拒绝不能覆盖已认领结果。
- 存储兼容：保留 v4，新增可选 receiver/rejected。旧 v4 记录可读；旧服务可能拒读新请求，
  新流程写入真实数据前必须重载更新后的插件，不混用旧写进程。本轮仅临时数据测试。
- 回滚：保留真实任务、聊天和工作区；不覆盖新写入、不删除聊天；新格式请求不能交给旧版本混写。

## 里程碑与并行边界

1. 固定请求、认领与拒绝语义；用户最新指令覆盖原独立验证门控。
2. 核心/MCP、UI、技能源独立并行修改；父代理负责插件入口、说明和整合。
3. 串行构建插件、验收 UI、检查源码/打包内容、更新现有插件。

## 验证方式与验收标准

- core/MCP：`pnpm test`、`pnpm smoke`、`pnpm verify:twoproc`；后台测试 60 秒硬超时。
- UI：类型检查、构建与协议自动化测试。用户明确要求停止模拟界面验收，
  后续在 Codex 原生宿主真实操作验收，本轮不再使用模拟界面宣布通过。
- 插件：`pnpm build:plugin`、`pnpm verify:plugin`，新增只读 host_info 不生成新面板或任务。
- 技能：检查实际工具签名与 SESSION_READY/先绑定流程，独立审查；不额外创建验证会话。
- 真实宿主：新协议在重载后的面板由用户手动运行 TASK-103；本轮不代替用户点击启动。
