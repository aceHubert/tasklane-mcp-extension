# 执行计划使用说明

执行计划用于超出单轮聊天上下文、需要多次推进或风险较高的任务。

## 什么时候创建计划

- 任务会跨会话、多个提交或多轮工作推进。
- 改动影响模块架构、MCP 契约、存储版本、数据迁移、并发锁或 Git/worktree 生命周期。
- 完成任务依赖阶段性验证、回滚策略或关键决策留痕。
- 多位贡献者或多个 Agent 需要持续协作。

## 存放位置

- 进行中的计划：[exec-plans/active/](exec-plans/active/)。
- 已完成的计划：[exec-plans/completed/](exec-plans/completed/)。
- 复用模板：[execution-plan.md](exec-plans/templates/execution-plan.md)。
- 明确推迟的债务：[tech-debt-tracker.md](exec-plans/tech-debt-tracker.md)。

计划文件使用简短的英文短横线名称，例如 `multi-repo-board-isolation.md`；归档时保留文件名并更新相关链接。

## 维护要求

- 写清目标、范围、背景、约束、风险、验收条件和验证方式。
- 推进过程和关键决定记录在仓库中，不只保留在聊天记录里。
- 状态变化时同步更新进度，说明阻塞点、下一步及负责范围。
- 并行工作写清依赖、文件负责人和整合顺序，避免多个 Agent 同时修改同一文件。
- 验证应与改动匹配：core/mcp 构建与测试、UI 类型检查与构建、stdio 冒烟、真实临时 Git、双进程存储、bridge 校验或浏览器交互。后台自动化测试设置最长 60 秒硬超时。
- 注明未验证项，不把计划中的检查写成已通过；浏览器独立模式与原生宿主验收分别记录。
- 涉及存储版本或 MCP 契约时，记录兼容策略、旧数据备份、并发访问及回滚方式；涉及 Git 时说明已有分支和 worktree 的保留策略。
- 完成后补齐验证结果并移至 `completed/`；取消或过期计划注明原因后归档，保证 `active/` 可信。移动操作遵循用户授权范围。
- 明确推迟的事项录入技术债表，关联计划并给出触发条件和后续动作。

仅维护计划及模板无需额外历史记录；实际实现按 [历史记录规范](HISTORY_GUIDE.md) 留档。
